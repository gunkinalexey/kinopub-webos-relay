# kinopub-webos-client

Веб-клиент [KinoPub](https://kino.pub) для телевизоров на webOS и обычных
браузеров. Каталог, поиск, фильтры, закладки, история, подборки, выбор
качества/аудио/субтитров и плеер с поддержкой Direct, Relay и HLS.

Ставится на свой сервер: приложение состоит из бэкенда-моста к API KinoPub и
статического фронтенда, всё поднимается одной командой через Docker Compose.

История изменений — в [CHANGELOG.md](CHANGELOG.md).

## Зачем нужен мост

**Главная причина — воспроизведение.** Если отдать телевизору прямую ссылку
на файл в CDN, видео запускается, но потом встаёт, а перемотка не работает.
Особенно заметно при возобновлении с середины: запрос превращается в
byte-range внутрь многогигабайтного файла, CDN отдаёт его слишком медленно,
буфер не наполняется никогда. Хуже всего, что элемент `<video>` при этом
**не сообщает об ошибке** — он просто висит с пустым буфером, и «Продолжить»
зависает молча. Проверено на 2160p HEVC: с 00:00 играет нормально, при старте
с 31:11 мёртв и через полминуты. В приложении из-за этого есть отдельный
сторож зависания, а поток по умолчанию идёт через мост, который забирает
файл сам и отдаёт телевизору ровным потоком.

Вторая причина — доступ к API. Браузер телевизора не может ходить в KinoPub
напрямую: там нет CORS, а токены нельзя держать в коде страницы.

Отсюда две ветки через один и тот же бэкенд:

```
телевизор / браузер
        │
        ▼
    nginx  :80                     ← отдаёт статику фронтенда
        ├── /            → index.html, app.js, styles.css
        └── /bridge/*    → backend:8000
                              │
                              ├── хранит сессию KinoPub (httponly-кука)
                              ├── проксирует и сжимает постеры
                              ├── проксирует видеопоток (Relay/HLS)
                              └── ходит в api.service-kp.com
```

Токены KinoPub живут только на сервере, в браузер уходит лишь `httponly`-кука
сессии. Сессии и настройки хранятся в SQLite (`/data/kp.db` в томе
`kp_data`); позиции просмотра своей копии не имеют — они читаются и пишутся
прямо в историю KinoPub, поэтому одинаковы на всех устройствах.

### Режимы потока

| Режим | Как идёт видео | Когда полезен |
|---|---|---|
| **Relay** | Файл целиком через мост | По умолчанию: ровное воспроизведение и рабочая перемотка |
| **HLS** | Мост нарезает поток | Когда нужен выбор дорожек на лету |
| **Direct** | Телевизор берёт файл из CDN сам | Единственный режим, доносящий HDR без потерь, но подвержен зависанию выше |

Переключается в Настройках. При зависании Direct приложение само уходит на
Relay, но один раз за сеанс — чтобы не дёргать туда-сюда рабочий поток.

## Требования

- Docker и Docker Compose v2
- ~1 ГБ на образы, 2 ГБ RAM с запасом
- Доступ к `api.service-kp.com` и `*.cdntogo.net`
- Действующая подписка KinoPub

Годится любой Linux-хост: отдельная машина, LXC на Proxmox, NAS. Для LXC
нужны `nesting=1,keyctl=1`, иначе Docker внутри не заведётся.

## Быстрый старт

```bash
git clone <адрес-репозитория> kinopub && cd kinopub
cp .env.example .env
```

В `.env` заполнить учётные данные клиента API (см. ниже) и разрешённые
CDN-домены:

```
KINOPUB_CLIENT_ID=<id>
KINOPUB_CLIENT_SECRET=<secret>
STREAM_HOST_SUFFIXES=service-kp.com,kino.pub,staticpop.net,cdntogo.net
```

```bash
docker compose up -d --build
```

Открыть `http://<адрес-сервера>:8080` и привязать устройство (см.
«Первый запуск»).

### Учётные данные клиента API

`KINOPUB_CLIENT_ID` / `KINOPUB_CLIENT_SECRET` — это идентификатор
**приложения**, а не вашего аккаунта. Доступ к личной библиотеке даёт
отдельная привязка устройства по коду, а не эти значения. Подходят публично
задокументированные учётные данные Kodi-плагина (`xbmc`) — то же, чем
пользуются сторонние клиенты KinoPub.

## Вариант А. Без обратного прокси

Самый простой путь: приложение доступно по адресу и порту сервера.

`docker-compose.yml` уже публикует порт:

```yaml
ports:
  - "8080:80"
```

В `.env`:

```
CORS_ORIGINS=http://192.168.0.50:8080
COOKIE_SECURE=false
```

Открывается как `http://192.168.0.50:8080`. Порт можно поменять на 80, тогда
адрес будет без него — но на порты ниже 1024 нужны права, а внутри Docker это
решается самим маппингом:

```yaml
ports:
  - "80:80"
```

Минусы: адрес с портом неудобно вводить на пульте телевизора, и при
добавлении других сервисов порты начнут путаться.

## Вариант Б. За обратным прокси

Позволяет открывать приложение по имени (`http://kinopub.lan`) и держать
рядом другие сервисы. Прокси ставится **отдельно**, перед приложением.

```
DNS: kinopub.lan → IP прокси
        ▼
   Caddy / nginx :80        ← роутинг по заголовку Host
        ▼
   этот проект :8080 → nginx → backend
```

Приложение при этом менять не нужно — порт продолжает публиковаться, прокси
обращается к нему как обычный клиент. В `.env` меняется только origin:

```
CORS_ORIGINS=http://kinopub.lan
```

### Caddy

```
http://kinopub.lan {
	reverse_proxy 192.168.0.50:8080 {
		flush_interval -1
	}
}
```

### nginx

```nginx
server {
  listen 80;
  server_name kinopub.lan;

  location / {
    proxy_pass http://192.168.0.50:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header Range $http_range;
    proxy_set_header If-Range $http_if_range;
    proxy_buffering off;
    proxy_read_timeout 24h;
  }
}
```

> **Самое важное при работе за прокси.** Настройки для видеопотока надо
> продублировать на внешнем прокси: отключить буферизацию, поднять таймаут
> чтения и пробрасывать `Range`/`If-Range`. Внутренний nginx проекта это уже
> делает, но внешний прокси оказывается **перед** ним. Без этого симптом —
> не ошибка, а плавающие подвисания при перемотке, которые долго ищутся.
> У Caddy буферизации нет по умолчанию, `flush_interval -1` закрепляет это
> явно; nginx буферизует и требует `proxy_buffering off`.

### Если прокси терминирует HTTPS

```
COOKIE_SECURE=true
CORS_ORIGINS=https://kinopub.example.com
```

## Настройки `.env`

| Переменная | Назначение |
|---|---|
| `KINOPUB_CLIENT_ID` / `_SECRET` | Учётные данные клиента API |
| `KINOPUB_API_BASE` | Адрес API, по умолчанию `https://api.service-kp.com` |
| `CORS_ORIGINS` | Origin'ы через запятую, с которых разрешены запросы |
| `COOKIE_SECURE` | `true` только если доступ по HTTPS |
| `STREAM_HOST_SUFFIXES` | **Белый список хостов** для проксирования видео и картинок |
| `MEDIA_REFERER` / `MEDIA_ORIGIN` | Заголовки к CDN, если он их требует |
| `IMAGE_REFERER` | Заголовок `Referer` для постеров |
| `IMAGE_MAX_BYTES` | Предел размера картинки |
| `AUDIO_HLS_*` | Временный HLS при пересборке звуковой дорожки |
| `WITH_FFMPEG` | `0` — образ без FFmpeg, меньше и быстрее собирается |

> **`STREAM_HOST_SUFFIXES` — источник самой обидной ошибки.** Список пуст —
> проксируется что угодно. Список заполнен — всё, чего в нём нет, получает
> `403`, включая постеры и видео. Значения должны быть **реальными** хостами:
> `staticpop.net` (постеры), `cdntogo.net` (видео). Оставленный из примера
> вымышленный домен вроде `example-cdn.net` даёт пустые обложки и неработающие
> Relay/HLS, при том что Direct продолжает играть — потому что идёт мимо
> прокси. Совпадение по суффиксу, домена второго уровня достаточно.

Переменные окружения применяются через `docker compose up -d`, пересборка
образа не нужна. Исключение — `WITH_FFMPEG`: он решает, что попадёт в образ,
и требует `docker compose up -d --build backend`.

## Первый запуск: привязка устройства

1. Открыть приложение — появится экран «Подключение устройства»
2. Нажать «Начать привязку устройства», появится код
3. Ввести код на [kino.pub/device](https://kino.pub/device)
4. Приложение подхватит авторизацию само

Сессия хранится в `/data/kp.db` внутри тома `kp_data` и переживает
перезапуск и пересборку контейнеров. Привязка нужна один раз.

### Перенос на другой сервер

Чтобы не привязывать устройство заново и не потерять историю просмотра,
достаточно перенести базу:

```bash
# на старом сервере
docker compose cp backend:/data/kp.db ./kp.db
# на новом, при уже запущенных контейнерах
docker compose cp ./kp.db backend:/data/kp.db
docker compose restart backend
```

## Обновление

```bash
git pull
docker compose up -d --build
```

Фронтенд смонтирован как том и подхватывается сразу после обновления
страницы — пересборка нужна только при изменениях в `backend/`.

## Тесты

Фронтенд — 312 проверок, обычные Node-скрипты без фреймворка. Четыре из
восьми файлов принимают путь к `app.js` **аргументом**; без него они падают
ещё до первой проверки и молча дают ноль строк:

```bash
cd frontend/tests && npm install
for f in harness actions episodes misc panel quality sections subs; do
  node $f.js ../app.js
done
```

Бэкенд — смоук-проверки. `smoke_test.py` не входит в образ (копируется
только `app/`), поэтому его нужно положить внутрь:

```bash
docker compose cp backend/smoke_test.py backend:/app/smoke_test.py
docker compose exec -T backend python smoke_test.py
```

## Частые проблемы

**Пустые обложки, не работает Relay/HLS, в логах `403`** — в
`STREAM_HOST_SUFFIXES` нет реальных хостов CDN. См. врезку выше.

**Долгая пауза и `KinoPub API timeout` / `502`** — API KinoPub периодически
недоступен, это внешняя проблема. Проверяется прямо:

```bash
docker compose exec backend python -c "import socket; s=socket.socket(); s.settimeout(5); s.connect(('api.service-kp.com',443)); print('ok')"
```

**`{"status":401,"error":"unauthorized"}` при живой сессии** — KinoPub отозвал
токен досрочно. Приложение обновляет его само при первом же 401; если и
обновление отклонено, устройство нужно привязать заново.

**Видео подвисает при перемотке за обратным прокси** — не проброшены
`Range`/`If-Range` или не отключена буферизация на внешнем прокси.

**Телевизор не открывает адрес по имени** — многие телевизоры игнорируют DNS
из DHCP и ходят во внешний резолвер. Адрес локального DNS прописывается в
сетевых настройках телевизора вручную.
