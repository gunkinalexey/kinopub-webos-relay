## backend 0.9.99 / v0.12.0 — Ревизия кода: кэши, скорость отклика и снос фейкового поиска

Разбор бэкенда и фронтенда по просьбе «найди баги и узкие места». Ниже —
только то, что подтверждено замером, а не «наверное станет быстрее».

### Самое неприятное: поиск молча подсовывал выдуманные фильмы

`api.js` делал так:

    search: ... request('/catalog/search?...').catch(() => request('/mock/search?...'))

то есть **любая** ошибка настоящего поиска (401, таймаут, сеть) тихо
подменялась ответом `/mock/search` — пятью захардкоженными карточками
(«Дюна», «Оппенгеймер», «Сёгун», «Бегущий по лезвию 2049», «Разделение») с
`streams: []` и градиентом вместо постера. Выглядит как результат, играть
нельзя. Ровно тот случай, который в этом проекте запрещён политикой «не
выдавать нерабочее за рабочее», — и сегодня, во время падения авторизации,
он бы отработал. Фолбэк убран, `/mock/search` и `MOCK_ITEMS` удалены,
смоук-тест теперь проверяет, что эндпоинта **нет** (404). Упавший поиск
показывает ошибку.

### Обложки: перезагрузка страницы стоила ~48 скачиваний и ~48 пережатий

Две независимые причины, обе исправлены:

- `state.cacheVersion` вычислялся как `Date.now()` прямо в литерале
  состояния, то есть **новый на каждую загрузку страницы**, и подставлялся
  в каждый URL картинки как `v=`. Из-за этого `Cache-Control: immutable,
  max-age=30d`, который прокси и так отдавал, не переживал ни одной
  перезагрузки. Теперь значение лежит в `localStorage` и меняется только
  кнопкой «Сбросить кэш».
- У `/image` не было **серверного** кэша: каждый запрос заново тянул файл
  со staticpop и заново гонял LANCZOS-ресайз с прогрессивным JPEG. Добавлен
  LRU на 96 МБ (ограничение по байтам, а не по числу записей — бэкдроп
  весит как двадцать постеров) плюс `ETag`/`If-None-Match`.

Замер: холодный запрос **480 мс**, повторный **4.4 мс**, условный — **304 и
0 байт**. `v=` намеренно не входит в ключ серверного кэша: он существует
чтобы обновлялись браузеры, и учитывать его здесь значило бы качать заново
идентичную картинку.

### Меньше походов в API

- **Счётчики страниц пережили перезапуск.** `page_count_cache` жил только в
  памяти, поэтому фоновый прогрев заново опрашивал все 12 разделов на
  каждом `docker compose up -d --build`. Появилась таблица `kv_cache`
  (key/payload/expires_at) — тот же 6-часовой TTL, но на диске. Проверено:
  12 записей на месте, следующий старт их переиспользует.
- **Жанры и страны** (`/catalog/genres`, `/catalog/countries`) ходили в
  KinoPub при каждом открытии панели фильтров в новой вкладке, хотя это
  справочники, которые не меняются. Кэш на 12 часов. Замер: 749 мс → 4 мс и
  130 мс → 4 мс.
- `/catalog/list` (кэш добавлен в 0.9.98) на повторе: 162 мс → 4 мс.

### Проверено, что ничего не сломано

312 фронтенд-проверок и все бэкенд-смоук-проверки зелёные. Фронтенд-тесты
запускаются в контейнере (`node` на хосте нет) и требуют путь к `app.js`
аргументом: `node <файл>.js ../app.js` — без него четыре из восьми падают
ещё до первой проверки и молча дают ноль строк PASS.

### Найдено, но не тронуто

Восемь символов в SVG-спрайте объявлены и нигде не используются: `i-tv`,
`i-subtitles`, `i-wifi`, `i-speed`, `i-chat`, `i-mail`, `i-ruble`, `i-send` —
следы незапущенных экранов. Мёртвых кнопок и пустых обработчиков в разметке
нет: все `id` из `index.html`, кроме спрайтов и двух контейнеров под CSS,
реально используются в `app.js`.

## v0.11.1 — Не грузились обложки: в белом списке хостов стоял пример из комментария

Пользователь сообщил, что не загружаются обложки. В логах бэкенда — сплошные
`GET /image?url=https%3A%2F%2Fm.staticpop.net%2F... 403 Forbidden`, при этом
тот же URL из контейнера тянулся напрямую нормально (200, `image/jpeg`,
40 КБ). Значит 403 отдавал не CDN, а мы сами.

Причина — в `.env`:

    # STREAM_HOST_SUFFIXES=service-kp.com,kino.pub,example-cdn.net
    STREAM_HOST_SUFFIXES=service-kp.com,kino.pub,example-cdn.net

строка-пример из комментария была продублирована уже без `#`, вместе с
выдуманным `example-cdn.net`. `/image` и `/stream` гоняют URL через общий
`validate_stream_url`, который при непустом списке пускает только
перечисленные суффиксы — а настоящих хостов там не было ни одного: постеры
лежат на `staticpop.net`, видео — на `*.cdntogo.net`.

То есть ломались не только обложки: **Relay/HLS-воспроизведение отваливалось
по той же причине**, просто Direct идёт мимо прокси и потому работал.

Заменено на реальные хосты (`service-kp.com,kino.pub,staticpop.net,cdntogo.net`).
Совпадение суффиксное, поэтому домена второго уровня хватает и на
`m.staticpop.net`, и на `<uuid>.ams-static-03.cdntogo.net`. Проверено:
постер через прокси теперь 200 `image/jpeg`, а посторонний хост по-прежнему
получает «Stream host is not allowed» — список продолжает работать, он просто
перестал состоять из плейсхолдеров. Меняется применением `docker compose up -d
backend` (переменная окружения, не пересборка образа).

## backend 0.9.99 / v0.11.0 — Выбор CDN-сервера KinoPub + замер скорости

KinoPub раздаёт видео с одного из нескольких своих CDN, и выбор живёт в
настройках **устройства** — в том же самом объекте, куда уже пишет
`/device/capabilities`. Проверено живьём переключением и перечитыванием
`v1/items/100468`:

    serverLocation=1 (Нидерланды) -> <uuid>.ams-static-NN.cdntogo.net
    serverLocation=3 (Россия)     -> <uuid>.msk-static-NN.cdntogo.net

то есть выбор реально меняет, откуда идут байты, а не просто подпись. Список
берётся из `v1/references/server-location` (не захардкожен — третий регион,
если появится, подхватится сам).

### Что появилось

- **`GET /servers`** — список регионов и текущий выбранный.
- **`POST /servers/select`** — ручное переключение, применяется сразу.
- **`POST /servers/measure`** — по очереди переключается на каждый регион,
  берёт свежий URL реального фильма и качает первые 3 МБ, замеряя скорость;
  отдельно меряет отклик (лучшее из трёх TCP+TLS-хендшейков). С
  `apply_best` оставляет победителя, иначе возвращает прежний выбор.
- **В «Настройках» — блок «Сервер раздачи»**: выпадающий список для ручного
  выбора и кнопка «Проверить скорость», которая показывает по каждому
  серверу скорость/отклик и сама включает быстрейший.

### Честные оговорки

- **Замер идёт со стороны моста, а не телевизора.** Мост сам проксирует
  Relay/HLS, поэтому его маршрут и решает скорость для всего, кроме Direct;
  при Direct телевизор ходит в CDN своим путём, и этого отсюда не измерить
  (в песочнице путь браузер→`*.cdntogo.net` вообще не работает, см.
  HANDOFF.md). В подсказке под блоком так и написано.
- **Победитель — не просто «больше Мбит/с».** Замер на 3 МБ шумный: один и
  тот же регион подряд дал 21.6 и 29.2 Мбит/с. Поэтому победа засчитывается
  только с отрывом >15%, а внутри этой полосы регионы считаются равными и
  решает куда более стабильный отклик. Без этого кнопка советовала бы разный
  сервер при каждом нажатии.
- Прогон переключает общую настройку аккаунта, поэтому он под `asyncio.Lock`
  (два параллельных прогона могли бы оставить аккаунт на чужом регионе), а
  прежний выбор возвращается в `finally`. Уже выданный плееру URL — полный
  подписанный адрес конкретного хоста, а не редирект, так что идущее
  воспроизведение проверка не рвёт.
- `v1/items/popular` **требует** параметр `type` (без него 400, не пустой
  список) и обязательно `movie`: у сериала вместо `videos[]` лежит
  `seasons[].episodes[]`, и проба выглядела бы как «нет потока».

## backend 0.9.99 — Мёртвая сессия больше не висит сутки

Найдено попутно и подтверждено живьём: `/auth/status` бодро сообщал «ещё ~24
часа», а любой реальный запрос к KinoPub возвращал
`{"status":401,"error":"unauthorized"}`. Причина — `refresh_if_needed`
смотрел только на часы: раз до `expires_at` далеко, токен не обновлялся
никогда, и сессия оставалась мёртвой до истечения записанного срока.

Теперь сигналом считается сам 401 от KinoPub: `kino_get`/`kino_post` при 401
один раз принудительно обновляют токен и повторяют запрос. Обновление — под
локом на сессию, и после захвата лока сессия перечитывается: если её успел
обновить параллельный запрос, берётся уже сохранённый токен, а не сжигается
ротированный refresh второй раз.

## backend 0.9.98 / v0.10.2 — Меньше запросов к api.service-kp.com

Повод: пока разбирались с предыдущими багами, апстрим KinoPub временно стал
недоступен (таймауты на уровне TCP-коннекта, не 401/429 — воспроизведено и с
хоста, и из контейнера, не связано с правками этой сессии). Заодно нашлось
два места, где бридж дёргал KinoPub чаще, чем нужно:

- **`/catalog/list` не кэшировался вовсе** — каждое открытие раздела, каждый
  возврат назад, каждая лишняя вкладка били напрямую в `v1/items*`.
  Содержимое каталога не персонализировано (отметки «просмотрено»/закладки
  приходят отдельными запросами — `/watching/statuses`, `/history` — не
  отсюда), так что 60-секундный TTL-кэш по (`endpoint`, `selector`, `page`,
  `perpage`) безопасен. Проверено живьём: одинаковый запрос дважды подряд —
  755мс (реальный поход к KinoPub), затем 9мс (отдано из кэша, до апстрима
  вообще не дошло).
- **`/profile` кэшировался (5 минут, см. `profile_cache`), но фронтенд сам
  обходил этот кэш** — `initializeAuthenticatedApp()` каждый раз звал
  `loadProfile(true)` (`refresh=true`), то есть каждая перезагрузка страницы
  форсировала свежий `v1/user`, хотя бэкенду для чипа подписки в шапке
  хватило бы и пятиминутной давности. Оставлено `refresh=true` только там,
  где это осмысленно — кнопка «Обновить статус» в модалке подписки
  (`refreshSubscription`).

## v0.10.0 — Иконки киноТёрка теперь из папки, а не зашиты в код

Раньше три собачьи иконки (`dog-icon-1/2/3.png`), которые ротируются в
режиме «киноТёрк», были жёстко прописаны по имени файла в `app.js` и
`index.html`. Теперь они лежат в `frontend/assets/dog/` — `nginx.conf`
отдаёт JSON-листинг этой папки (`autoindex on; autoindex_format json;` на
`/assets/dog/`), и `app.js` при загрузке страницы читает его и берёт **все**
файлы `.png/.jpg/.jpeg/.gif/.webp`, что там лежат на момент запроса.
Никакой сборки не нужно — фронтенд и так живой bind-mount без билд-шага
(см. HANDOFF.md): просто положить/убрать файл в `assets/dog/`, обновить
страницу — список обновится. Если листинг недоступен (старый nginx.conf,
офлайн), остаётся встроенный фолбэк на три исходных файла. Проверено
живьём: докинул четвёртый файл в папку без пересборки контейнеров — тут же
появился в `GET /assets/dog/`.

Заодно сама иконка в левом верхнем углу (`.brand-logo-img`) в режиме
киноТёрка увеличена на 20% — с 34px до 40.8px (в режиме kinopub размер не
менялся).

## backend 0.9.97 — Зелёные ссылки в карточке стали настоящими, и заодно нашёлся баг в поиске

Пользователь показал таблицу «Информация» и попросил сделать зелёные бейджи
(жанр, страна, режиссёр, актёры, год) реально кликабельными — и прислал
образец с самого kino.watch: `movie?years=2026;2026`,
`item/search?query=<имя>&mode=director|actor`.

### Что стало ссылкой и куда она ведёт

- **Жанр/Страна** — клик открывает раздел этого тайтла (Фильмы/Сериалы/…) с
  панелью фильтра, уже открытой и с выбранным значением. Только если у
  жанра/страны в ответе KinoPub реально есть числовой id — панель фильтрует
  по id, не по названию, а `v1/collections`-подобные текстовые списки без id
  ничего отфильтровать не могут. Бэкенд теперь отдаёт `genres_detailed`/
  `countries_detailed` (`[{id,title}]`) рядом со старыми текстовыми
  `genres`/`countries` — если id нет, бейдж остаётся обычным зелёным текстом,
  не мёртвой ссылкой.
- **Год выхода** — клик фильтрует тот же раздел на этот ровно один год
  (`year_from=year_to=<год>`), как `movie?years=2026;2026` на сайте.
- **Режиссёр / В ролях** — клик по одному имени (не по всей строке сразу)
  запускает поиск в режиме «Режиссёры»/«Актёры» — те самые вкладки, что уже
  были в поиске.

### Баг, который был там ещё до этой задачи

Проверил живьём клик по режиссёру «Дени Вильнёв» — поиск вернул **ноль**
результатов. Оказалось: режимы поиска «Актёры»/«Режиссёры» в этом бридже были
декоративными с самого начала — `mode` из фронтенда никуда не передавался,
и запрос уходил в KinoPub ровно тем же способом, что и режим «Все».

На `kinoapi.com/api_video.html` у `v1/items/search` (в описании самого
поиска, легко не заметить) документирован настоящий параметр
`field=title|director|cast`. Проверил вживую: `field=director` для «Дени
Вильнёв» — 13 тайтлов, `field=cast` для актёра — 37, `field=title` сузило
выдачу так же, как раньше это делал самодельный клиентский фильтр. Параметр
был всё это время рабочим — просто никогда не отправлялся.

Подключил `SEARCH_MODE_FIELDS` (`title→title`, `actor→cast`,
`director→director`, `all→` без параметра — поиск по всем полям, как и
задокументировано). Старая клиентская дощипка для режима «title» больше не
нужна — теперь то же самое честно делает сам API.

Проверено вживую: клик по «Дени Вильнёв» → 26 тайтлов, первый — «Дюна: Часть
вторая»; клик по «Тимоти Шаламе» → 44; клик по жанру «Боевик» → раздел
«Фильмы», панель открыта, `id=2` выбран; страна и год — так же.

Тесты: 304 → 312 (фронтенд: id-ссылки и plain-text фолбэк, все пять типов
кликов с проверкой параметров запроса; бэкенд: 31 → 36, включая
`SEARCH_MODE_FIELDS` и `_id_name_list`).

## backend 0.9.94 — «Длительность»: серии считаются иначе, чем фильмы

Пользователь попросил конкретный расчёт для сериалов: «одной серии ≈
00:58:26 / (58 мин), всего сериала: 2 дн. 23 час. 6 мин.», а для фильмов —
длительность первой серии, если их несколько.

### Почему это не одна формула на всё

KinoPub отдаёт `duration.average`/`duration.total` для любого тайтла, даже
для фильма. Разница в том, что означает список `videos`/`media` под этими
числами. Проверил вживую на «Дюна: Часть вторая»: там **две** записи —
«24 fps» и «48 fps», это **альтернативные версии одного фильма**, не
последовательные части. `duration.total` для неё — 19965 (сумма обеих
версий, ~5ч33м), при настоящем хронометраже фильма ~2ч47м. У сериала те же
поля означают ровно то, что должны: «Тед Лассо» — `average: 2496`,
`total: 89877` (реальная средняя серия и реальная сумма 36 серий).

Складывать альтернативные версии бессмысленно, поэтому для фильма эти два
поля игнорируются целиком, а не только «total»: берётся длительность
**первой** записи с реальным числом (`детали Часть вторая` → 10016с →
`02:46:56 / (167 мин)`, ровно хронометраж фильма). Для сериала — наоборот,
используются оба общих числа как есть.

### Как теперь выглядит строка

- **Сериал** (`type`: serial/docuserial/tvshow — докусериал и ТВ-шоу устроены
  так же, проверено вживую): `одной серии ≈ HH:MM:SS / (NN мин), всего
  сериала: X дн. Y час. Z мин.`. Нулевые старшие разряды опускаются — часовой
  докусериал пишет «1 час. 23 мин.», а не «0 дн. 1 час. 23 мин.».
- **Фильм** (и концерты/докфильмы/3D): просто `HH:MM:SS / (NN мин)` — как и
  раньше, но по первой записи, а не по потенциально бессмысленной сумме.

Секунды при подсчёте общей длительности сериала сперва округляются до минут
целиком, а уже потом раскладываются на дни/часы/минуты — иначе 59.6
«округлённой вверх» минуты могла бы разъехаться на «0 час. 60 мин.».

Проверено вживую на четырёх реальных тайтлах через бридж и в самом
приложении: «Тед Лассо» — `одной серии ≈ 41:36 / (42 мин), всего сериала:
1 дн. 0 час. 58 мин.`; «Дюна: Часть вторая» — `02:46:56 / (167 мин)`, не
сумма версий; «Оппенгеймер» (один файл) — `03:00:22 / (180 мин)`; докусериал
«Убийства в день матча» — `одной серии ≈ 41:35 / (42 мин), всего сериала:
1 час. 23 мин.` — без лишнего «0 дн.».

Тесты: 280 → 283 (движок форматирования, реальный сериал из фикстуры,
отдельный кейс на фильм с двумя версиями, который раньше сложил бы их).

## backend 0.9.93 — Сборка без FFmpeg одной строкой в .env

`WITH_FFMPEG=0` в `.env` — и образ бэкенда собирается вообще без ffmpeg.
Замерено на этой машине: **900 МБ → 273 МБ**, и apt при выключенном флаге не
дёргается вовсе, так что сборка ещё и заметно быстрее (раньше это был самый
долгий шаг пересборки без кэша). Это закрывает вопрос «нужен ли вообще
ffmpeg», который висел открытым в HANDOFF.

Флаг идёт и в `build.args` (решает, что попадёт в образ), и в `environment`
(что об этом знает приложение). Поэтому меняется он **пересборкой**, а не
рестартом:

```bash
docker compose up -d --build backend
```

### Что теряется, а что нет

FFmpeg нужен ровно одной функции — последней ступени выбора звука: пересборке
дорожки на сервере, когда в самом потоке её нет (`/audio-hls/jobs`). Всё
остальное его не касается: каталог, воспроизведение во всех трёх режимах
(direct/relay/HLS), субтитры и первые три способа переключить звук (дорожки в
манифесте, родные дорожки MP4, другой HLS-вариант). Проверено на сборке без
ffmpeg: каталог, `/play` (16 ссылок) и «Похожие» отвечают как обычно.

### Флагу на слово не верим

`_ffmpeg_available()` требует двух вещей сразу: чтобы `WITH_FFMPEG` не был
выключен **и** чтобы `ffmpeg`/`ffprobe` реально нашлись через `shutil.which`.
Переменная, обещающая программу, которой в образе нет, хуже отсутствия
переменной: запрос дошёл бы до `create_subprocess_exec` и умер бы
`FileNotFoundError` внутри фоновой задачи, где плееру уже нечего показать
пользователю. Проверено обратное: на образе без ffmpeg даже при
`WITH_FFMPEG=1` возможность честно сообщается как отсутствующая.

### Чтобы это не выглядело поломкой

- `/health` отдаёт `ffmpeg: true|false`.
- `POST /audio-hls/jobs` без ffmpeg отвечает 503 с текстом, который можно
  показать как есть, а не падает где-то в фоне.
- Плеер спрашивает это на старте и **не отправляет запрос вовсе**: выбранная
  дорожка возвращается к прежней, а в строке ошибки пишется причина — вместо
  мигания «Готовим дорожку…», обречённого на неудачу.
- Если `/health` недоступен, состояние остаётся «неизвестно» и поведение
  ровно прежнее — не отключаем функцию, которая, скорее всего, работает.
- В диагностике появилась строка «FFmpeg на сервере».

Проверено на обеих сборках: с ffmpeg — `ffmpeg: true`, `/usr/bin/ffmpeg` на
месте; без — `ffmpeg: false`, `command -v ffmpeg` пусто, `/audio-hls/jobs`
даёт 503, остальное работает. Тесты: 276 → 280, бэкенд 26 → 29 (смоук зелёный
на обеих сборках).

## Фокус не убегал бы, счётчик считал не то, «Мои сериалы» и кнопки серий

Четыре замечания подряд, все фронтенд, бэкенд не трогался.

### Подсветка оставалась на «Новинках», куда бы вы ни ушли

Пользователь: наведено на «ТВ Шоу», а подсвечена «Новинки». Воспроизвёл сразу:
клик по «ТВ Шоу» — и `document.activeElement` становится «Новинки».

Причина в одной строке: `route()` заканчивался на `setTimeout(focusFirst,20)`, а
`focusFirst()` — это «сфокусировать первый `.focusable` в документе». Первый
`.focusable` в `index.html` — буквально кнопка «Новинки» (строка 49). То есть
**любая** навигация утаскивала фокус в начало сайдбара.

С мышью это косметика, с пультом — нет: кольцо фокуса стоит не там, где фокус
на самом деле, и следующее нажатие «вниз» уезжает от «Фильмов», а не от
«Спорта».

Теперь фокус остаётся на том контроле, который пользователь нажал, а когда его
никто не держит (переход по хэшу, кнопки браузера назад/вперёд, первая
загрузка) — встаёт на раздел, куда мы попали. Отдельно разобраны «3D» (своей
кнопки в сайдбаре нет, живёт в переключателе «Фильмы / 3D», который
`renderTop()` пересобирает) и вкладки «Популярные/Свежие/Горячие».

Два бага поймал сам тест, а не браузер: `<body>` проходил проверку «фокус
держит живой элемент» (поэтому проверка теперь требует именно `.focusable`), и
видимость нельзя определять через `offsetParent` — в jsdom нет layout, там все

## backend 0.9.90 — Фильтр выглядит как на сайте, и рейтинги оказались настоящими

Пользователь прислал скриншот панели фильтра kino.pub и попросил такой же
дизайн. Panel переписана: ряд селектов, ряд двуручных слайдеров с зелёной
шкалой и «пузырьками» значений, красная кнопка слева и зелёная справа —
структура и цвета как на скриншоте.

### Заодно выяснилось, что прошлый вывод про рейтинги был неверным

В README ниже (и в докстринге `/catalog/list`) было написано, что рейтинговых
фильтров «нет ни в документации, ни в `conditions`». Это оказалось ошибкой, и
она стоила панели двух контролов. Поля есть, называются `imdb_rating` и
`kinopoisk_rating`. Проверено тремя способами:

- `conditions[]=imdb_rating>=8` роняет type=movie с ~31 990 до ~795, и все
  вернувшиеся тайтлы действительно с оценкой ≥ 8;
- `imdb_rating>=7` вместе с `imdb_rating<=8` складываются в настоящую полосу;
- выдуманное поле (`bogus_field>=8`) **не меняет** счётчик вообще — вот это и
  доказывает, что настоящие два поля именно распознаются, а не «эндпоинт
  игнорирует все условия одинаково».

Так что оба слайдера со скриншота — «Рейтинг Кинопоиска» и «Рейтинг IMDb» —
сделаны по-настоящему.

### Но не в том виде, в каком они на сайте

На сайте у рейтингов шаг 0.1. Проверил — **KinoPub отбрасывает дробную часть
условия**: `imdb_rating>=7`, `>=7.1`, `>=7.5` и `>=7.9` дают одинаковые 8444
страницы, то же самое с `<=` и с полем Кинопоиска. Ручка, показывающая 7.5, а
фильтрующая по 7, — ровно тот случай, который в этом проекте не отгружается.
Поэтому шаг рейтингов **целый**, и подписи на шкале целые. Бэкенд округляет
вниз, а не к ближайшему: вниз — это в точности то, что делает сам KinoPub, а
округление 8.6 → 9 молча выкинуло бы тайтлы, которые сырое API вернуло бы.

Второй честный нюанс: верхняя граница ловит и тайтлы вовсе без оценки, то
есть читается как «не выше X или без рейтинга».

### Слайдер, который работает с пульта

Прошлая версия панели специально не делала слайдеров: «на пульте нет
указателя». Это было верно про перетаскивание и неверно про слайдеры.
Реализация:

- **Одна точка фокуса на слайдер, а не две.** Две ручки на одной шкале имеют
  перекрывающиеся прямоугольники, а `move()` выбирает цель по центрам
  прямоугольников — различить их он не смог бы в принципе, а при равных
  значениях они вообще совпадают.
- **OK** — вход в режим правки, **OK** ещё раз — переключение края,
  **← →** — двигают край, **Назад** — выход. Подсказка прямо под шкалой.
- **Стрелки перехватываются только в режиме правки.** Вне его они уходят
  глобальному обработчику, так что слайдер не может запереть фокус.
- **Коммит с задержкой 450 мс**: иначе каждый шаг перезапрашивал бы каталог,
  а зажатая кнопка пульта даёт ~30 повторов в секунду. Одна серия нажатий —
  один запрос (закреплено тестом).
- **Фокус переживает перерисовку.** Панель пересобирается на каждое
  изменение фильтра, и без явной передачи фокуса пользователь вылетал из
  контрола после первого же нажатия — на пульте фокус это единственный
  курсор. Ловилось живьём: `document.activeElement` к моменту сборки новой
  панели уже `<body>`, потому что `renderTop()` очищает `#catalogTop`
  раньше, — поэтому id запоминается до очистки.
- Мышь работает как на сайте: клик и перетаскивание по шкале двигают
  ближнюю ручку, без всякого режима правки.

Два бага, пойманных живьём по дороге: «пузырьки» на краях шкалы вылезали на
соседний слайдер (теперь сдвиг зависит от позиции: 0 % → 0, 100 % → −100 %), и
выход из режима правки коммитил фильтр **до** сброса общего флага, из-за чего
перерисованная панель поднималась обратно в режиме правки — выйти было нельзя.

### Что в панель не попало и почему

Со скриншота не сделаны «Субтитры», «Возраст», «Язык», «Перевод», «Озвучка»,
«Хочу AC3», «Без рекламы», «Хочу HD / Без HD». Каждое имя пробовалось живьём
как параметр `v1/items` (`subtitles`, `subtitle`, `age`, `lang`, `language`,
`translation`, `voice`, `ac3`, `advert`, `hd`, `nohd`, `uhd`) — все до одного
вернули нефильтрованный счётчик. «Хочу 4K» отдельным чекбоксом не нужен: это
и есть «Качество → 4K», которое работает.

**«Мне повезёт!» сделана по-настоящему**, а не декоративной кнопкой: каталог
и так сообщает число страниц под текущим фильтром, так что она берёт
случайную страницу внутри него, случайный тайтл на ней и открывает карточку.
Если фильтр даёт три тайтла — выберет один из этих трёх.

Проверено вживую через бридж: `imdb_from=8` → 133 страницы вместо 5332, в

## backend 0.9.89 — Direct и HDR: приложение само отбирало их у телевизора

Пользователь: «не запускается direct и не цепляется hdr, а раньше работало».
Прошлый заход списал это на сторож зависания (`watchDirectStall`) — это была
не та причина, симптом остался. Настоящая нашлась в том, что появилось
одновременно с ней: в отчёте о возможностях устройства.

### Что происходило

Приложение отвечало KinoPub на три вопроса — HEVC, 4K, HDR — результатами
проб браузера. Проблема в том, что проба даёт **три** ответа, а код понимал
два: «да» и «нет». Третий — «браузер не понял вопроса» — молча превращался
в «нет».

- **HEVC.** Спрашивали ровно одной строкой: `hvc1.1.6.L120.B0`. Браузеры
  webOS сплошь и рядом отвечают на неё пустой строкой на железе, которое
  этот файл проигрывает без запинки, — и знают при этом голое `hvc1`.
- **HDR.** Спрашивали `matchMedia('(dynamic-range: high)')`. Этот
  media-запрос появился в Chromium 98 / Safari 13.1, то есть **позже**
  браузера в большинстве телевизоров. Несуществующая фича даёт
  `matches === false`, неотличимое от честного «нет».

Дальше — цепочка, проверенная вживую на `v1/items/100468`, переключая флаги
устройства и перечитывая выдачу:

```
supportHevc=1 support4k=1 -> 2160p/1080p/720p/480p h265
supportHevc=0 support4k=1 -> 2160p/1080p/720p/480p h264
```

`supportHevc=0` — и KinoPub на **каждый** тайтл отдаёт лестницу h264. Нет
HEVC-файла → нет HDR-файла → нечего играть через direct (`preferredModeFor`
включает direct только для HEVC). Один непонятый вопрос про кодек уносил обе
функции разом.

Вторая половина беды: запись устройства в KinoPub **одна на весь бридж**, не
одна на браузер. Это видно прямо в аккаунте — на момент разбора там стояло
`supportHdr: 0` при `supportHevc: 1`. И это воспроизвелось живьём во время
починки: заход в приложение с обычного десктопа честно сообщал «мой монитор
не HDR» — и снимал флаг у телевизора.

Сам `preferredModeFor` добивал: право вето на direct имела одна строка
`canPlayType`. Direct — единственный транспорт, который доносит HDR до
видеоплоскости (через MSE/hls.js webOS роняет его в SDR), и он отключался
по ответу, которому нельзя верить.

### Что сделано

- **Пробы кодеков спрашивают несколько написаний** (`hvc1.1.6.L120.B0`,
  `hev1.…`, `hvc1.2.4.…`, голые `hvc1`/`hev1`) и берут лучший ответ. Одно
  «probably» где угодно — это поддержка.
- **Появилось состояние «не знаю»** — и оно больше никогда не становится
  «нет». Проверка на доверие простая: если браузер не признаётся даже в
  H.264, его `canPlayType` декоративный, и его молчание про HEVC ничего не
  доказывает (`codecProbesTrustworthy`). Для media-запросов признак —
  сериализация в `not all`.
- **Бэкенд не пишет то, чего ему не говорили.** `CapabilitiesPayload` стал
  трёхзначным (`Optional[bool]`), `None` — «оставь как есть». Раньше поля
  приводились к `bool`, и «не знаю» уезжало в KinoPub как ноль.
- **HDR в авторежиме больше не снимается никогда** — только утверждается или
  не трогается. Основания: в этих телевизорах запроса просто нет; запись
  описывает LG-телевизор; переключение `supportHdr` вживую **не меняло**
  список файлов ни у одного из 25 проверенных 4K-тайтлов, то есть заявить
  его ничего не стоит; а десктоп, отвечающий честно, иначе продолжал бы
  обкрадывать телевизор.
- **Direct больше не зависит от одной строки `canPlayType`.** Если браузер
  молчит — direct пробуется: не сможет декодировать, обработчик `error` и
  сторож переключат на relay за секунды, и это несравнимо дешевле, чем
  никогда не давать HDR. Явное «нет» (браузер отвечает на другие вопросы, а
  на HEVC говорит «нет») по-прежнему уводит в hls.js, где MSE ещё может его
  вытянуть.
- **Настройка «Возможности устройства»**: «Определять автоматически» /
  «Телевизор: HEVC + 4K + HDR» / «Только H.264». Явный профиль перекрывает
  любые пробы — и в отчёте KinoPub, и в выборе качества, и в выборе
  транспорта. Сохранение сразу отправляет флаги и пишет в статус, что
  KinoPub теперь про устройство думает.
- **Диагностика показывает обе стороны**: ответы проб браузера, можно ли им
  верить, что мы сообщаем, — и рядом реальные флаги из
  `v1/device/info` (новый `GET /device/state`). В прошлый раз ответ лежал
  там всё это время; теперь он виден на самом телевизоре.

### Проверено

Вживую: матрица флагов на реальном аккаунте (таблица выше); пустой отчёт о
возможностях больше ничего не перезаписывает (`skipped: [support4k,
supportHdr, supportHevc]`, `changed: []`); полная загрузка приложения с
десктопа больше не снимает `supportHdr` (до фикса — снимала). Реальный ответ
`/play` прогнан через настоящий `app.js` на пяти профилях устройств: любой
правдоподобный webOS (молчащие пробы, только голое `hvc1`, полные пробы,
принудительный профиль «Телевизор») даёт **2160p h265 через direct**;
десктоп без HEVC — hls, честное `hevc:false` и `hdr:null`.

Тесты: фронтенд 223 → 233, бэкенд 17 → 21, всё зелёное. Стаб `matchMedia` в
`quality.js` заодно исправлен на правдивый — раньше он возвращал `false` на
незнакомый запрос вместо `not all`, то есть воспроизводил ровно ту ошибку,
которую тестировал.

**Профиль устройства сейчас выставлен в «Телевизор»** — на LG это даёт HDR
детерминированно, независимо от того, что ответит его браузер. Если нужно
обратно на автоопределение, это одна строка в настройках.

`direct` теперь просто не запускается.

Причина — `watchDirectStall()`, добавленный этой же сессией для другого
бага (зависание «Продолжить» на большом файле): жёсткий дедлайн 12 секунд
на пустой буфер, без разницы между «зависло навсегда» и «просто медленно
грузится». Реальный 4K/HDR файл на настоящей сети ТВ вполне может собирать
первый буфер дольше 12 секунд, оставаясь при этом рабочим — сторож выдёргивал
его на relay/HLS (который на webOS обычно роняет HDR в SDR через MSE),
теряя именно то, ради чего вообще стоило пытаться играть direct.

Сторож теперь слушает событие `progress` на `<video>`: если хоть один байт
пришёл за окно ожидания — это не «зависло», а «медленно», и таймер просто
продлевается ещё на одно окно (с потолком в 60 секунд суммарно, на случай
совсем патологической капели). Ничего не пришло вообще — как и раньше,
переключение на relay/HLS по расписанию (это и есть исходный баг с
byte-range-запросом в большой файл, который сторож изначально чинил, — тот
сценарий не тронут).

Проверено тестами (`quality.js`): «прогресс продлевает окно», «без прогресса
всё равно переключает» — оба зелёные, было 214 проверок, стало 217. Живая
проверка в этой песочнице показала нестабильную картину для direct-режима на
одном и том же файле (иногда сразу успешно, иногда всё равно уходит в HLS
после 12+ секунд без единого байта) — это может быть особенностью сетевого
пути именно этой тестовой среды до CDN KinoPub, а не логики самого сторожа.
Нужна повторная проверка на реальном ТВ.

## backend 0.9.86 — «Закладки»: счётчик папки и список карточек расходились

Пользователь сразу поймал: папка «йоу» показывала «5 тайтлов», а при открытии

## v0.9.91 / backend 0.9.84 — Качество: фильм открывается в максимуме, который тянет устройство

Разбор всей цепочки выбора качества. Нашлись четыре независимые причины, по
которым «максимальное качество» не получалось, — и одна из них отменяет вывод
из прошлой сессии про «4K-бейдж врёт».

### 1. Главное: KinoPub отдаёт РАЗНЫЕ файлы в зависимости от флагов устройства

Проверено причинно, а не по совпадению: переключал флаги устройства и
перечитывал `v1/items/124450`.

| Флаги устройства | Какие файлы отдаёт KinoPub |
|---|---|
| `support4k=1, supportHevc=1` | **2160p h265**, 1080p h265, 720p, 480p |
| `support4k=0, supportHevc=1` | 1080p h265, 720p, 480p |
| `support4k=0, supportHevc=0` | 1080p **h264**, 720p, 480p |

Последняя строка — ровно то, что я видел во время разбора «4K-бейджа»:
проверил тогда 46 тайтлов, ни у одного не было 2160p-файла, и сделал вывод,
что поле `quality: 2160` в каталоге — враньё. **Вывод был неверный.**
Устройство в тот момент было объявлено как не поддерживающее 4K/HEVC, поэтому
KinoPub физически не показывал 4K-файлы. Бейдж всё это время говорил правду.
Хорошо, что правку «убрать бейдж» отклонили.

### 2. Флаги устройства были захардкожены в `true`

v0.9.82 слала `support4k: true, supportHevc: true` вслепую. Для этого браузера
угадала, но в общем случае это опасно ровно наоборот: браузеру **без** HEVC
KinoPub отдал бы HEVC-only список, который тот не сможет проиграть вообще.

- Новый **`POST /device/capabilities`** ([main.py](backend/app/main.py))
  принимает реальные возможности от фронтенда и пишет их в
  `v1/device/{id}/settings` — только те флаги, что действительно изменились.
- Фронтенд честно пробует декодеры (`canPlayType` + `MediaSource`) **с учётом
  уровня**: `hvc1.1.6.L120` (1080p) и `hvc1.1.6.L150` (2160p) — это разные
  вопросы, устройство может уметь 1080p HEVC и не уметь 4K. Плюс
  `matchMedia('(dynamic-range: high)')` для `supportHdr`.
- Синхронизация идёт один раз при старте, а `play()` её **дожидается** —
  иначе первый же запуск сессии получил бы список файлов от прошлого профиля.

### 3. HLS-ссылки всех качеств — это ОДИН И ТОТ ЖЕ мастер-плейлист

Проверено: ссылки на «2160p», «1080p» и «720p» побайтово одинаковые, и в
каждой перечислены все четыре рендишена (3840x2160 / 1920x1080 / 1280x720 /
720x406, `VIDEO-RANGE=PQ` — то есть HDR там есть). То есть в HLS-режиме
рендишен выбирает ABR hls.js, а не мы, а селектор качества перезагружал
идентичный манифест — чистая бутафория. ABR стартует с осторожной оценки
полосы, поэтому 4K-фильм открывался в 1080p.

- `applyHlsLevelPreference()` на `MANIFEST_PARSED` ставит `startLevel` на
  лучший разрешённый рендишен (открывается сразу в максимуме) и
  `autoLevelCapping` — потолок из настроек, выше которого ABR не полезет.
- Ручной выбор качества в HLS-режиме теперь двигает уровень hls.js
  (`currentLevel`), а не перезагружает тот же манифест. Проверено вживую:
  переключение 2160p → 720p меняет реально декодируемое с 3840x2160 на
  1280x720 **без паузы и пере-буферизации**, время продолжает идти.

### 4. Direct-поток намертво зависал при «Продолжить»

Отдельный настоящий баг. 2160p-файл в режиме direct с позиции 00:00 играет
прекрасно (`readyState 4`, буфер набирается). Тот же файл с сохранённой
позиции 31:11 — `readyState 1`, буфер **пустой**, и так бесконечно (проверял
27 секунд). Событие `error` при этом не приходит вообще, поэтому существующий
откат по ошибке никогда не срабатывал — «Продолжить» просто вис.

- Сторож `watchDirectStall()`: если через 12 секунд у direct-потока пустой
  буфер, это считается несостоявшимся стартом и включается relay/HLS с той же
  позиции. Пустой буфер — намеренно строгий критерий: живой, пусть и медленный
  4K-старт успевает набрать хоть что-то задолго до этого.
- `fallbackFromDirect()` больше не требует флага `hdrAttempt`: не начавшийся
  direct-поток стоит перевести на relay независимо от того, почему его выбрали.
  От зацикливания по-прежнему защищает одноразовый `hdrFellBack`.

### 5. Мелочи, которые тоже мешали

- `bestPlayableGroupIndex()` при неудаче возвращал `groups.length-1` —
  **самый низкий** вариант. То есть устройство, не прошедшее проверку кодека,
  получало 480p, который оно всё так же не могло декодировать, только хуже.
  Теперь деградация идёт по-человечески: лучший декодируемый в пределах
  потолка → лучший декодируемый вообще (потолок — предпочтение, а не повод не
  играть) → самый крупный, чтобы было что показать и на чём честно упасть.
- Варианты, которые устройство не декодирует, **вообще не показываются** в
  списке качества. Если не декодируется ни один — показываются все с пометкой
  «не поддерживается», потому что пустой список ничего не объясняет.

Проверено вживую на реальном 4K-тайтле: «Продолжить» → 2160p, декодируется
3840x2160, буфер 125 с, воспроизведение идёт. Тесты: 184 проверки, 0 падений
(было 159; +25 новых на выбор качества, уровни HLS, сторож зависания и отчёт
о возможностях).

**Замечание про настройки этого аккаунта.** В сохранённых настройках стояло
`Качество: До 1080p` и `Режим потока: HLS relay` — при них максимум был
физически недостижим (жёсткий потолок 1080p) и HDR тоже (MSE обычно роняет
HDR в SDR, прямой путь к декодеру телевизора не использовался). Переключил
на `Максимум, что тянет устройство` и `Авто` — это и есть запрошенное
поведение; поменять обратно можно в Настройках.

## v0.9.89 — Кнопка нативного полного экрана в плеере, чинит двойной тогл паузы

Два связанных запроса про плеер:

- **Всегда должна быть возможность переключиться в нативный плеер** (не
  только через настройку «Полный экран в плеере», которая применяется один
  раз в момент нажатия «Смотреть»). Новая кнопка `#nativeFullscreen` в ряду
  иконок плеера (между «вперёд 10 сек» и «закрыть») зовёт
  `requestFullscreen()` прямо на `<video>`, а не на `#playerLayer` —
  переключает в полноэкранный режим независимо от текущей настройки, в любой
  момент воспроизведения. Именно полноэкранный режим самого `<video>` (а не
  контейнера вокруг него) обычно и передаёт вывод на аппаратную
  видеоплоскость телевизора — тот же механизм, что уже описан в v0.9.68 как
  нужный для HDR passthrough; кнопка даёт добраться до него, не переоткрывая
  плеер и не меняя настройку заранее. Повторное нажатие (или системная
  кнопка «назад») выходит обратно; если на момент нажатия уже был активен
  полноэкранный режим `#playerLayer` (обычная настройка `layer`), сначала
  выходит из него и только потом просит полный экран на видео — попытка
  запросить fullscreen на новом элементе поверх уже активного на другом
  не везде срабатывает надёжно.
- **Починен баг «пауза и тут же снова play» в нативном полноэкранном видео.**
  Причина — ровно та, которую подсказал пользователь: `#playerLayer` вешает
  свой клик-обработчик (пробел/тап = пауза/плей) на весь контейнер, а
  `<video>` — его дочерний элемент, так что клик по видео всё равно
  всплывает и долетает до этого обработчика. Пока видео не в fullscreen,
  это единственный обработчик паузы — ничего не дублируется. Но когда
  именно `<video>` становится fullscreen-элементом, платформенный
  (браузер/ТВ) нативный оверлей полноэкранного видео перехватывает тот же
  клик и **сам** переключает паузу/плей — независимо от нашего JS. Один
  клик пользователя = два независимых переключения (нативное и наше),
  что и выглядело как «остановилось и тут же снова запустилось». Обработчик
  `#playerLayer`.onclick теперь проверяет `fullscreenElement()===video` и
  ничего не делает в этом случае — нативный оверлей сам справляется со своим
  же кликом.

Оба изменения — `frontend/app.js` и `frontend/index.html`, без бэкенда;
проверено набором фронтенд-тестов (159/159 зелёных, включая существующие
проверки на `fullscreen`), и вживую — кнопка в DOM, обработчик навешан,
ошибок в консоли нет. Настоящее нативное HDR-переключение и точное
воспроизведение двойного тогла проверить в headless-браузере нельзя (нужен
реальный ТВ/плеер с фактическим HDR-дисплеем и его платформенным
полноэкранным UI) — логика исправлена по описанному пользователем механизму,
не просто предположительно.

## v0.9.81 (backend) — Прогресс просмотра доходит до настоящей истории KinoPub

Жалоба: «История просмотров» (`/catalog/history`, `v1/history`) переставала
пополняться. Причина в архитектуре, а не в баге — этот бридж проксирует
воспроизведение через собственный relay/HLS, так что сервер KinoPub физически
не видит сам факт просмотра; `PUT /history` до сих пор писал позицию только в
локальную SQLite этого моста. Нужны те же ручки `v1/watching/*`, что уже
нашлись для раздела «Я смотрю» (см. v0.9.80 ниже) — на этот раз
`marktime` (отметка позиции) и `toggle` (принудительно просмотрено/не
просмотрено), обе с `kinoapi.com/api_watching.html`.

Проверял вживую на реальном эпизоде («Стюарт Блум», S01E02) через
`/bridge/explorer`, туда-обратно, чтобы не оставить эпизод помеченным иначе,
чем было:

- **`v1/watching/marktime?id=&video=&season=&time=`** — `video` это порядковый
  номер серии в сезоне (не внутренний id видео), тот же, что уже считает
  `collect_media` (`entry.episode`/`entry.season`). Первые пробы с этими же
  параметрами один раз вернули `body: null` без эффекта — похоже на разовую
  неполадку на стороне KinoPub, не проблему параметров: повторный чистый вызов
  с теми же `id/video/season` сработал как в документации
  (`{"status":200}`), позиция реально сохранилась. Отдельно подтвердилось:
  если отправить `time`, равное или больше `duration` эпизода, KinoPub сам
  переводит `status` в 1 (просмотрено) — `marktime` в одиночку покрывает и
  обычный прогресс, и завершение.
- **`v1/watching/toggle?id=&video=&season=`** — явный переключатель
  просмотрено/непросмотрено, **не set, а именно flip**. В лоб вызывать его при
  каждом «досмотрели серию» опасно: плеер зовёт сохранение прогресса и на
  `pause`, и на `ended` для одного и того же завершения (`pause` у HTML5-видео
  срабатывает непосредственно перед `ended`) — два подряд `toggle` откатили
  бы уже помеченный эпизод обратно в непросмотренные. Подтверждено вживую:
  два подряд «завершённых» сохранения без защиты действительно гасят пометку.
  Поэтому `toggle` используется только как подстраховка поверх `marktime` (на
  случай расхождения локально измеренной `video.duration` с канонической
  длительностью KinoPub) и только после проверки текущего статуса через
  `v1/watching?id=` — если эпизод там уже `watched`, `toggle` не зовётся.

**Backend**

- `ProgressPayload` получил `season`/`episode_number` — порядковые номера,
  которых раньше в локальном `/history` не было вовсе (там жил только

- `PUT /history` стал `async`, получил `kp_session`, и после локальной записи

  `videos[]` для фильма) в переиспользуемую функцию: теперь нужен и в самой
  ручке, и в защите `toggle` от отката.

**Frontend**

- `play()` теперь на старте эпизода запоминает `state.episodeSeason`/

## v0.9.88 — Кнопка «назад» браузера и раздел не теряется при обновлении

Оба требования — назад/вперёд браузером и «остаться в том же разделе после
F5» — закрыты одним механизмом: URL hash. Установка `location.hash` сама по
себе настоящая навигация (создаёт запись в истории, стреляет `hashchange`
на назад/вперёд), так что не понадобилось городить `pushState`/`popstate` —
только закодировать текущий экран в hash и один обработчик `hashchange`,
который перечитывает hash и разворачивает нужный экран (включая тот, что
уже стоит в адресной строке при самой первой загрузке страницы).

- `#route/<name>` — раздел каталога/настройки, `#details/<id>` — карточка
  тайтла, `#search/<mode>/<query>` — поиск. `route()`, `openDetails()`,
  `doSearch()` в конце сами прописывают свой hash (`pushHash()` в
  [app.js](frontend/app.js)); `applyHash()` — единственное место, которое
  на это реагирует, что при `hashchange`, что при первой загрузке.
- Кнопка «← Назад» на экране описания и клавиша «назад» на пульте больше не
  дёргают `closeDetails()` напрямую, а зовут `history.back()` — иначе экран
  закрывался бы, а запись в истории браузера оставалась бы висеть,
  рассинхронизируя реальный адрес и то, что видно на экране.
- Плеер закрывается при любой навигации по hash (тот же список guard'ов,
  что уже был у клавиши пульта).
- `pushHash()`/`applyHash()` явно проверяют `typeof location==='undefined'`
  — тестовый набор гоняет `app.js` через голый Node без реального
  `location`/`history` (стенды в `frontend/tests/*.js` это подтверждают:
  `route()`/`openDetails()`/`doSearch()` вызываются там напрямую), без этой
  проверки все 159 проверок упали бы на первом же вызове `route()`.

Проверено вживую: назад/вперёд корректно переключает разделы, обновление
страницы на `#details/<id>` и на `#search/...` восстанавливает именно тот
экран, кнопка «Назад» корректно возвращает в каталог/поиск, откуда
открывали карточку.

## v0.9.85 — Второй источник «просмотрено»: v1/watching напрямую

По итогам анализа неиспользуемых методов KinoPub API (см. предыдущий разбор
в истории чата, не в этом файле) — подключил `GET v1/watching?id=`:
настоящий, отслеживаемый по всем устройствам статус просмотра конкретного
тайтла, в отличие от `/watching/statuses` (сканирует до 20 страниц
`v1/history` целиком — годится для каталога, но избыточно для одного
тайтла).

- **Новый эндпоинт `GET /catalog/items/{id}/watching`** ([main.py](backend/app/main.py))
  оборачивает `v1/watching?id=`. Пришлось разбирать ДВЕ разные формы ответа:
  у фильма — плоский `item.videos[]`, у сериала — `item.seasons[].episodes[]`
  (раньше код проверял только первую форму, для любого сериала эпизоды
  молчаливо не находились). Также поле `status` там принимает -1
  (не смотрели) / 0 (смотрели частично) / 1 (посмотрели); `bool(status)`
  считает -1 истиной, так что первая версия помечала как просмотренное вообще
  всё подряд — заменил на явную проверку `== 1`.
- **Карточка серии теперь учитывает оба источника «просмотрено»** — свой
  локальный `/history` (только то, что смотрели через этот клиент) и
  реальный статус KinoPub (учитывает официальный сайт/другие устройства).

  на оба сигнала.
- **Настоящий баг, а не гипотетический**: `loadItemProgress`/
  `loadItemWatching` перерисовывали ленту серий тем же `item`, что был
  передан в `openDetails` — **черновиком карточки** без `.seasons`/`.media`
  (у полного тайтла эти поля появляются только после отдельного
  `KPApi.item(id)`, который сохраняется в `state.current`, а не в исходный
  аргумент). Пока `/history` успевал ответить раньше `KPApi.item()` — это
  было незаметно; добавление более медленного `/watching` (у сериала на
  267 серий это реальный объём) сделало гонку почти гарантированной: лента
  серий рендерилась правильно, а затем стиралась в пустоту, когда медленный
  запрос наконец возвращался. Обе функции переключены на чтение
  `state.current` вместо захваченного по замыканию `item` — перепроверено
  вживую несколько раз подряд, включая намеренно короткие и намеренно
  длинные задержки перед проверкой.

## v0.9.84 — Карусель серий: постраничная, с точками, отмечает просмотренное

Продолжение прошлой правки карусели серий — по фидбэку с реальными
скриншотами оказалось, что скролл-с-стрелками-поверх был не тем, что нужно:

- **Постраничная, а не скролл.** Раньше это был `overflow-x:auto` с двумя
  стрелками поверх карточек — стрелка перекрывала крайнюю карточку и могла
  перехватывать клик вместо неё, а последняя видимая карточка нередко
  влезала только наполовину. Теперь `.episode-strip` двигается через
  `transform:translateX` строго кратно ширине «страницы» (сколько карточек
  целиком помещается), так что на границе страницы никогда не остаётся
  обрезанная карточка. `.episode-viewport` дополнительно обрезан по
  `max-width`, пересчитываемому под конкретное число карточек — без этого
  `flex:1` растягивал видимую область шире, чем ровно N карточек, и
  следующая карточка чуть проглядывала из-под обрезки.
- **Стрелки — соседи по флексу, не оверлей.** Больше не позиционируются
  поверх карточек (`position:absolute`) — теперь они обычные элементы в
  строке рядом с `.episode-viewport`, той же высоты, что и сами карточки
  (`align-items:stretch`), поэтому у них физически нет возможности
  перекрыть или перехватить клик по карточке.
- **Точки снизу** — по одной на «страницу» карусели, кликабельны, крупнее
  прежнего черновика (18px, активная — 44px, по просьбе после первого
  показа).
- **Отмечает просмотренные серии.** Карточка серии теперь показывает те же
  оверлеи «ПРОСМОТРЕНО»/«ПРОДОЛЖИТЬ», что и карточка в каталоге — раньше
  этих данных на карточке серии не было вовсе, хотя `state.detailsProgress`
  уже загружался для кнопки «Продолжить». `loadItemProgress` теперь
  перерисовывает и ленту серий, а не только кнопки, когда прогресс
  подгружается (гонка: полные данные тайтла и локальный прогресс приходят
  раздельными запросами).
- **При открытии сериала карусель сама встаёт на первую непросмотренную
  серию** (и нужный сезон, если сезонов несколько) — не всегда серия 1.
  Если весь сериал просмотрен, показывается последний блок карусели, а не
  первый. Спойлер-фрагмент кода (`firstUnwatchedIndex`/
  `firstUnwatchedInSeasons`) использует ту же таблицу прогресса.
- **«Серия 1» больше не подписывается у фильма.** Кнопка «Продолжить» для
  одиночного файла (фильма) показывала подпись «Серия 1» — синтетическая
  заглушка бэкенда для файла без собственного названия, нужная только
  списку серий сериала, просочилась туда, где сравнивать вообще не с чем.
  `episodeLabel` теперь ничего не показывает, если у тайтла всего один файл.
- **Скролл над сайдбаром больше не скроллит сайдбар.** У `.sidebar` есть
  свой `overflow:auto` (список секций может не влезать по высоте) — колесо
  мыши над ним перенаправляется на текущий видимый экран вместо
  проскролливания самого меню.

## v0.9.79 — История: правильные даты, серия/сезон, кадр вместо обложки

Три связанные проблемы в «Истории» (`/catalog/history`, реальная история
просмотров KinoPub — не путать с локальным `/history` этого моста):

- **Все записи показывали «1 января 1970 г.»**, и казалось, что раздел не
  обновляется новыми просмотрами. Причина — `_history_entry_item` в
  [main.py](backend/app/main.py) выбирала дату записи через `_pick_first(
  entry, ['created','updated','time','date','last_seen','watched_at'])`, а
  реальный ответ KinoPub `v1/history` вообще не содержит `created`/
  `updated`/`date`/`watched_at` — зато содержит `time` (сколько секунд
  просмотрено, не когда) и `counter`, которые есть почти всегда и потому
  подхватывались раньше настоящей метки `last_seen`. «Просмотрено 373
  секунды» читалось как «просмотрено в 00:06:13 1 января 1970» — и так для
  каждой записи, отчего все они проваливались в один и тот же фиктивный
  день независимо от реальной даты. Приоритет исправлен на `last_seen` →
  `first_seen` (настоящие unix-таймстампы) — даты сразу стали настоящими и
  разными.
- **Сезон/серия теперь показываются, если применимо.** `media.snumber`/
  `media.number` в ответе KinoPub (0/отсутствует для фильма) — это и есть
  сезон и серия конкретного просмотра; раньше это никак не отображалось, и
  сериал в истории показывал один и тот же тайтл десятки раз без разницы
  между карточками. Бэкенд отдаёт их как `history_season`/`history_episode`
  плюс уже готовый `media_title` (название серии); фронтенд собирает из
  них `S01E02 · Название серии` в подписи карточки (`historyEpisodeTag` в
  [app.js](frontend/app.js)) — только когда оба числа реальны, для фильма
  подпись остаётся прежней (оригинальное название).
- **Кадр серии вместо обложки, настраиваемо.** `media.thumbnail` в ответе —
  это реальный кадр, вырезанный именно из этого файла серии, а не постер
  всего сериала. Новая настройка «Кадр серии вместо обложки в истории»

  истории показывает этот кадр вместо обложки, но только когда есть

## v0.9.77 — Размер страницы каталога подгоняется под ровную сетку

Раньше `perpage` всегда было жёстко зашито как 48, независимо от того,
сколько карточек реально помещается в строку сетки (`.poster-grid` — CSS
`repeat(auto-fill, minmax(165px,1fr))`, число колонок зависит от ширины
экрана). Если в строку помещалось, скажем, 7 карточек, 48 давало 6 полных
строк и одну «хвостатую» из 6 карточек — на каждой странице, кроме
последней.

Теперь фронтенд перед запросом раздела читает уже посчитанный браузером
`getComputedStyle(...).gridTemplateColumns` (без дублирования логики
auto-fill), получает число колонок и берёт число строк, ближайшее к `50/cols`,
так что `perpage = rows*cols` — ровный прямоугольник, а сумма держится около
50: 7 в строке → 7 строк (49), 8 в строке → 6 строк (48), 6 в строке → 8
строк (48). `perpage` теперь пробрасывается в `/catalog/list` и
`/catalog/page-count` (бэкенд уже поддерживал произвольный `perpage`,
менять его не пришлось) вместо захардкоженных 48 с обеих сторон.

## v0.9.76 — Слёт авторизации в разделе показывает экран входа, а не сырую ошибку

На ТВ обнаружился случай: сессия умирает не при загрузке (там уже была

поиска, тот же экран сам перезагружается после успешного входа.

## v0.9.75 — Скрыт выбор сезона/серии там, где выбирать нечего

Backend всегда группирует медиа хотя бы в один псевдо-сезон
(`entry.get('season') or 1`), поэтому даже одиночный фильм с одним файлом
получал `item.seasons = [{'number': 1, 'episodes': [фильм]}]` — непустой
список. Фронтенд проверял только `!seasons.length`, а это условие после такой
группировки никогда не срабатывает, поэтому пилюля «Сезоны: 1» и лента из
одной серии рисовались даже для фильма.

Правило теперь такое:

- **2+ реальных сезона** — пилюли сезонов, как раньше.
- **1 сезон (в том числе синтезированный) с несколькими сериями** —
  плоская лента серий без пилюль: это плоский мини-сериал без разбивки по
  сезонам у KinoPub, показывать выбор из одного пункта незачем.
- **Один файл** (большинство фильмов) — ни пилюль, ни ленты; кнопки
  «Смотреть»/«Продолжить» уже достаточно.

Код `S01E01` на карточке серии и в подписи «Продолжить» теперь тоже показывается
только при реальных нескольких сезонах — для плоского списка серий он был
формальностью без объекта сравнения (сезон один и тот же для всех серий).

## Автоматический коммит и пересборка

`.claude/settings.json` вешает хук `Stop`, который после каждого ответа Claude
запускает [.claude/hooks/checkpoint.sh](.claude/hooks/checkpoint.sh): коммитит
изменения и пересобирает backend, если он менялся.

Почему именно так:

- **`Stop`, а не `PostToolUse`.** Один ответ обычно содержит десяток правок;
  на `PostToolUse` это дало бы десяток коммитов и минуты пересборок на одно
  логическое изменение.
- **Только `backend/`.** Фронтенд смонтирован как read-only bind mount, его
  правки видны сразу — пересобирать нечего.
- **Не `rebuid_containers.bat`.** Он заканчивается `pause` (в хуке это висело бы
  до таймаута) и использует `build --no-cache`, то есть переустанавливает ffmpeg
  на каждый запуск. Скрипт остаётся для ручной полной пересборки; хук вызывает
  `docker compose up -d --build backend` с кэшем.
- `examples/` добавлен в `.gitignore`: 14 МБ чужих ассетов, и в каждой странице
  живой `csrf-token` той сессии, в которой её сохранили.

Отключить или отредактировать — через `/hooks`.

## v0.9.71 — Авторизация сбрасывалась после привязки устройства

Ответ `POST /auth/device/poll` объявлял `Content-Length: 0`, неся при этом
23 байта тела. Причина — `JSONResponse(..., headers=dict(response.headers))`:
копия заголовков внедрённого пустого `Response` приносила его `content-length: 0`,
а Starlette не перезаписывает длину, заданную вызывающей стороной.

Клиент читал ноль байт, `r.json()` падал, и ветка «authorized» не выполнялась —
хотя `Set-Cookie` при этом доходил и сессия на сервере создавалась. Экран
привязки оставался на месте, пользователь привязывал устройство заново, и каждая
попытка добавляла ещё одну сессию в базу. Токены при этом были совершенно
исправны: срок 24 часа, refresh-токен на месте.

- Cookie ставится на тот ответ, который реально возвращается, без копирования
  чужих заголовков.
- Если опрос всё-таки не удался, клиент сперва переспрашивает `/auth/status` и
  считает привязку успешной, если сессия уже активна.
- В Диагностике появились строки «Сессия», «Refresh-токен» и «Токен истекает
  через».

Проверка на неопределённые имена (`pyflakes`, `eslint no-undef`) добавлена в
обиход после регрессии 0.9.70 — она же поймала бы её сразу.

## v0.9.68 — Полноэкранный режим плеера

Пикселей это не добавляет: слой плеера и так `position:fixed; inset:0`, видео
растянуто на весь вьюпорт, а браузер webOS сам по себе полноэкранный. Смысл в
другом — ТВ-браузеры обычно отдают полноэкранное видео **аппаратной
видеоплоскости** вместо композитинга страницы, а именно она делает
HDR-passthrough и аппаратное масштабирование 4K. Это тот же механизм, что и
Direct вместо MSE.

Повышение до видеоплоскости, как правило, требует полного экрана на самом
элементе `<video>`, а не на контейнере, — поэтому режим выбирается в настройках:

- **Оболочка плеера** (по умолчанию) — свои кнопки, таймлайн и меню остаются;
- **Само видео** — лучший шанс на HDR, но управление становится системным;
- **Выключен**.

Запрос делается синхронно в момент клика по «Смотреть»: к моменту ответа API
окно пользовательской активации уже закрыто и браузер откажет. Отказ
перехватывается и не ломает запуск. Закрытие плеера выходит из полного экрана;
выход по кнопке пульта не путается с закрытием плеера.

В Диагностику добавлены строки **Декодируется** (реальные `videoWidth×videoHeight`
— видно, приехал ли настоящий 4K) и **Полный экран** (режим и активность).

## v0.9.67 — Максимальное качество картинки под возможности устройства

Раньше по умолчанию всегда играл 1080p H.264, а 2160p HEVC оказывался
последним в списке кандидатов — даже 720p H.264 обходил 1080p HEVC. Поскольку
10-битный цвет и HDR у KinoPub приезжают именно в HEVC, вместе с разрешением
терялся и диапазон цветов.

**Ранжирование потоков (backend)**

- `choose_best_stream` больше не «целится в 1080p». Порядок: разрешение по
  убыванию → HEVC перед H.264 при равном размере → простой HTTP-файл, чтобы
  клиент мог отдать его аппаратному декодеру.
- Прежняя формула `abs(height - 1080)` штрафовала 2160p ровно так же, как 0p,
  поэтому 4K не выбиралось никогда.
- Поток получает флаги `hevc`, `hdr` и `bitrate` (HDR определяется по полю
  KinoPub, а если его нет — по строке качества).

**Выбор под устройство (frontend)**

- Возможности проверяются один раз: `canPlayType` и `MediaSource.isTypeSupported`
  для HEVC Main10 и H.264, плюс `(dynamic-range: high)` и `(color-gamut: p3)`.
- Берётся самый высокий вариант, который устройство реально декодирует. Нет
  HEVC — тихо откатывается к H.264, а не падает.
- Для HEVC, который декодируется аппаратно, используется прямое
  воспроизведение: MSE (hls.js) на webOS обычно роняет HDR в SDR, а нативный
  путь отдаёт файл декодеру телевизора.
- Если прямой поток не открылся, один раз происходит откат на relay/HLS с
  сохранением позиции и понятным сообщением.
- Настройка «Качество» наконец работает — теперь это потолок:
  авто / 2160p / 1080p / 720p. Явно выбранный режим потока имеет приоритет.

**Диагностика** показывает, что устройство реально умеет: ответ `canPlayType`
по H.264 и HEVC, наличие MSE, HDR-дисплей, гамут P3, текущий потолок и то,
какой вариант и транспорт играют сейчас.

Оговорка: приложение работает во встроенном браузере webOS, и переведёт ли он
панель в HDR-режим — зависит от платформы, а не от клиента. 10-битный HEVC даёт
выигрыш по бандингу в любом случае; включился ли настоящий HDR, покажет
Диагностика и индикатор HDR на самом телевизоре.

## v0.9.64 — Ложная ошибка «play() interrupted by pause()»

`video.play()` возвращает промис, который отклоняется с `AbortError`, если до
фактического старта воспроизведения элемент поставили на паузу или перезагрузили.
Это происходит при **каждом** переключении качества, дорожки и потока и при
закрытии плеера — то есть штатно. Код передавал текст этой ошибки в `mediaError`,
и поверх плеера появлялось «The play() request was interrupted by a call to
pause(). Позиция 00:00 сохранена».

- Прерванный запуск (`AbortError` или сообщение с `interrupted`) больше не
  считается ошибкой воспроизведения.
- Попытка запуска привязана к номеру переключения потока: отказ, относящийся к
  уже смененному потоку, игнорируется.
- `NotAllowedError` (блокировка автозапуска браузером) теперь показывает
  осмысленное «Нажмите OK, чтобы начать воспроизведение», а не общую ошибку.
- Настоящие ошибки (например, неподдерживаемый кодек) по-прежнему показываются.
- Приписка «Позиция … сохранена» выводится, только когда позиция действительно
  больше нуля.

## v0.9.61 — Переключение звука без FFmpeg, когда это возможно

Смена дорожки идёт по лестнице: FFmpeg включается только если в самом потоке
действительно одна дорожка.

1. **hls.js alternate audio** — если в манифесте есть `#EXT-X-MEDIA:TYPE=AUDIO`,
   дорожка меняется на месте. Позиция и перемотка не затрагиваются вообще.
2. **Нативные `video.audioTracks`** — работает на LG webOS при Direct-воспроизведении
   MP4. Desktop Chrome их не отдаёт и проваливается на следующий шаг.
3. **Другой HLS-вариант KinoPub** — backend (`GET /media/audio-variants`) проверяет
   `hls4`, `hls2`, `hls` и сообщает, сколько в каждом альтернативных аудиодорожек.
   Первый подходящий вариант перезагружается с сохранением позиции. Результат
   проверки кэшируется, поэтому следующие переключения бесплатны.
4. **Серверный remux** — прежний путь через FFmpeg, теперь только как fallback.

Исправления:

- `import re` отсутствовал, хотя `re.split` вызывался при слиянии дублирующихся
  media-узлов: карточка сериала могла падать с 500.
- `/catalog/items/{id}/play` запрашивает `media-links` не только когда нет потоков,
  но и когда `audios` короче, чем заявляет `tracks`, и **дополняет** список вместо
  замены. Это основная причина «в меню одна дорожка».
- `result.audios || result.media.audios` во фронтенде никогда не срабатывал:
  пустой массив истинный, поэтому список из media-узла терялся.
- Дорожка адресуется позицией в списке (`-map 0:a:N`), а не `audios[].index`.
  Прежний код выводил из `index` абсолютный номер потока: при 0-based payload
  вторая дорожка отображалась на первую, а обложка в MP4 сдвигала индексы.
- Убраны `-bsf:v h264_mp4toannexb` (HLS-муксер ставит фильтр сам), `discardcorrupt`
  (молча выбрасывал пакеты при переподключении к CDN) и `first_pts=0`
  (рассинхрон при старте не с нуля).
- Набор HTTP-опций FFmpeg определяется по установленному бинарю: неизвестная
  опция фатальна и убила бы задачу до старта.
- Упавшая задача больше не удерживает ключ дедупликации — повтор запускает новый
  процесс, а не отдаёт тот же труп до истечения TTL.

Внешние субтитры не зависят от выбора дорожки ни на одном из шагов.

# KP TV — webOS-oriented KinoPub bridge

Лёгкий TV-веб-клиент и FastAPI-прослойка для браузеров LG webOS.

## Реализовано

- Device Flow с динамическим `verification_uri`, таймером и повторным получением кода;
- сохранение пользовательской сессии в SQLite;
- автоматическое обновление access token;
- mock API для разработки без реального каталога KinoPub;
- главная страница, поиск, карточка фильма/сериала и список серий;
- настройки качества, режима потока, языка, субтитров и анимаций;
- локальная серверная история просмотра и восстановление позиции;
- прямое воспроизведение, byte-range relay, HLS relay и локальный HLS для выбранной озвучки;
- переписывание URL в HLS playlist, включая аудио, ключи и субтитры;
- защита relay от localhost/private IP и проверка redirect;
- управление пультом, восстановление фокуса между экранами;
- диагностика кодеков и тест произвольного URL в трёх режимах;
- backend/frontend media-логи.

## Запуск

```bash
cp .env.example .env
# заполнить KINOPUB_CLIENT_ID и KINOPUB_CLIENT_SECRET
docker compose up --build
```

Откройте `http://IP_СЕРВЕРА:8080` в браузере телевизора.

## Что работает без KinoPub API

Главная, поиск, карточки, сериалы, настройки и история работают через `/mock/*`. В демонстрационных карточках нет видеоссылок. Для проверки плеера откройте **Диагностика** и вставьте доступный вам URL.

## Следующий этап

Снять реальные JSON-ответы каталога, карточки, сезонов и файлов KinoPub и реализовать один backend-adapter, преобразующий их во внутренние модели клиента.

## Production

Задайте `STREAM_HOST_SUFFIXES`, включите HTTPS и `COOKIE_SECURE=true`. Для публичного многопользовательского сервиса добавьте шифрование токенов at-rest, CSRF-защиту и rate limiting.


## API Explorer (v0.6.0)

После авторизации откройте кнопку **API Explorer** в верхнем меню. Explorer выполняет только GET-запросы через текущую backend-сессию.

- путь вводится без домена и без начального `/`, например `v1/items`;
- query-параметры вводятся отдельно: `page=0&perpage=20`;
- OAuth endpoint заблокирован;
- access/refresh token, cookie, secret и похожие поля маскируются;
- максимальный размер диагностического ответа — 2 MB;
- ответ можно скопировать или скачать как JSON.

Точные пути KinoPub API зависят от актуальной версии сервиса. Explorer нужен, чтобы безопасно снять структуру реальных ответов и затем написать нормализующий adapter. Не публикуйте скачанные ответы без просмотра: в данных аккаунта могут быть персональные сведения, даже если токены уже замаскированы.

## Как работает переключение звука в v0.9.60

KinoPub HLS обычно содержит только одну дорожку, а метаданные остальных озвучек относятся к исходному HTTP-файлу. Поэтому клиент не пытается переключать несуществующие HLS audio groups. При выборе дорожки backend:

1. проверяет абсолютный индекс через FFprobe;
2. запускает FFmpeg с `-c:v copy` и AAC 2.0 для звука;
3. создаёт EVENT HLS по 4 секунды на сегмент;
4. возвращает плееру URL после появления достаточного диапазона;
5. продолжает подготовку в фоне, расширяя доступный диапазон перемотки.

При закрытии плеера, возврате на «Авто», смене качества или режима активная задача останавливается. Временные данные находятся в `/data/audio_hls`.
